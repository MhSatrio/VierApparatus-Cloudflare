Raw data are the record of what was measured, and their integrity is the basis of every later result. They should be stored in a location that is protected from accidental change, with a record of their origin, such as the instrument, the date and the person who collected them. A checksum, which is a short code computed from the file's contents, allows any later alteration to be detected. Sandve et al. (2013) recommended that raw data be treated as immutable, since a single silent edit can alter every result that depends on it.

A consistent directory structure separates raw data from processed and analysis-ready data. The raw directory is not written to by any analysis, and the processed directory is populated only by the pipeline. This separation makes the flow of data visible and prevents a derived file from being mistaken for an original. Wilkinson et al. (2016) described how such clarity supports findability, and it also helps a new team member understand the project quickly.

File names should state the content, the date of collection and the version where it matters. A name that encodes these facts allows a reader to identify the right file without opening it, and it avoids the confusion of files named final or revised. Peng (2011) argued that the path from the data to the result must be explicit, and consistent naming is the simplest way to show that path in the file system.

Derived datasets should be produced by scripts that read the raw data and apply recorded transformations. Manual edits to a derived file cannot be traced, and copies made by hand diverge over time as one is changed and the other is not. The project should check periodically that every derived dataset can be regenerated from the raw data, since a dataset that cannot be regenerated is a dataset whose origin is unknown.
