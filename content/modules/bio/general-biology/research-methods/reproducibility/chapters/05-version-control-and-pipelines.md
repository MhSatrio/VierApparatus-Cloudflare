Version control records every change to the code of an analysis, and it allows any past state to be recovered. A repository that contains the scripts, the configuration files and the documentation gives a complete history of how a result was produced. Sandve et al. (2013) recommended version control as one of the basic practices of reproducible computing, since it answers the question of which code produced which result.

Raw data should never be modified. They are stored as received, with a record of their origin, and every processed dataset is regenerated from them by the pipeline. This separation prevents a silent correction from altering the basis of the analysis, and it allows the processing to be checked at each stage. Peng (2011) argued that the chain from raw data to result is the substance of reproducibility, and a pipeline that makes this chain explicit serves that purpose.

Automated workflows rerun the analysis whenever an input changes, so that the outputs are always consistent with the current inputs and code. They reduce the risk that a figure is left out of date after a change, a common error in projects that are revised over time. Munafò et al. (2017) argued that such automation supports transparency, since every output can be traced to its inputs.

A release is a tagged state of the repository that corresponds to a submitted or published version of a study. Tagging makes it possible to return to the exact code behind a manuscript, even after the code has continued to change. Commit messages should explain why a change was made, not only what changed, so that the history itself documents the reasoning. Sandve et al. (2013) noted that such documentation is valuable to collaborators and to the investigator in later years.
