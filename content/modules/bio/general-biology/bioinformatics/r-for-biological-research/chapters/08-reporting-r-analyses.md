A report of an R analysis should allow a reader to rebuild the results from the raw data. This requires a chain of scripts, in which each script reads the output of the previous one, and a final step that produces every figure and table. The chain is the audit trail of the analysis. Peng (2011) argued that the figure in a paper should be regenerated by the code that produced it, and Sandve et al. (2013) listed the same requirement among their rules.

Literate documents combine code, output and text. R Markdown and Quarto documents run the code, insert its results into the text and render a document in which every number can be traced to a line of code. The documents are useful for reporting because the text and the numbers cannot drift apart, but they must be rendered from a clean session, so that the output reflects the code and not the state left by earlier runs.

Data provenance is part of the report. The source of each dataset, the date of retrieval, the version and the processing steps should be stated, since a dataset that has been revised may give different results. Where a dataset has been filtered, the criteria and the number of samples removed should be reported.

The statistical methods must be specified in detail. The test or model, its design, the handling of missing values, the correction for multiple testing and the threshold for significance are all required. Ioannidis (2005) described how undisclosed flexibility in these choices inflates the rate of false findings, and a report that states them allows a reader to judge how much the choices matter.

Love et al. (2014) show how an analysis can report effect sizes with shrunken estimates and their uncertainty, which is a practical model for reporting. A result stated with its size and its uncertainty is more informative than a bare list of significant genes.
