A unit test runs a function on an input whose correct output is known and checks that the function returns it. A test for a sequence filter might supply three short records, one of which is below the length limit, and check that only the other two are returned. Taschuk and Wilson (2017) described tests of this kind as a basic defence against errors in research software, since a function that passes its tests is known to behave as specified on those inputs, and a later change that breaks it is caught immediately.

Tests are only as good as the cases they cover. They should include the ordinary case, the boundary cases such as an empty file or a record of length exactly equal to the limit, and the malformed cases that the input may contain. A test that passes for typical data but fails on an edge case is valuable, because the edge case is where biological data most often surprise an analysis.

Version control records every change to the code. A version control system stores each version of each file, the author and the date of each change and a message that describes it. Peng (2011) argued that the ability to return to the exact state of an analysis is central to the credibility of computational results, and version control provides that ability.

Good practice is to make small, well-described changes. A commit that changes one function and states why it was changed can be reviewed and, if necessary, reversed. A commit that changes many things at once makes it hard to determine which change caused a new result. Results that are generated by the code should be tagged with the version of the code that produced them.

Sandve et al. (2013) recommended keeping a record of the version of each tool used in an analysis, and version control is the most practical way to keep the record of the code itself.
